# tree-sitter-teyru

A [tree-sitter](https://tree-sitter.github.io/tree-sitter/) grammar for Teyru,
the Java-like language whose compiler lives in this repository.  The grammar
was written against the compiler, not against Java:

- `docs/language.md` and `docs/diagnostics.md` for the language as documented,
- `internal/lexer/lexer.go` for the tokens (what is a keyword, what a number,
  where a string or a text block ends),
- `internal/parser/parser.go` for the shapes (what is a declaration, where a
  pattern is allowed, which reading wins when two are possible),
- `tests/programs/*.teyru` and `lib/*.teyru` for the surface that has to parse.

## Layout

```
grammar.js            the grammar
src/parser.c          generated parser (checked in, as tree-sitter expects)
src/grammar.json      generated
src/node-types.json   generated
src/tree_sitter/      tree-sitter's own headers, copied in (MIT, see ../../THIRD-PARTY-NOTICES.md)
queries/highlights.scm  highlighting, including Teyru's properties and val
queries/locals.scm      scopes, definitions and references
queries/indents.scm     what indents, and where
test/corpus/*.txt       the parser tests, one file per feature area
```

## Using it

### Neovim

With [nvim-treesitter](https://github.com/nvim-treesitter/nvim-treesitter),
point it at this directory and build the parser:

```lua
-- lazy.nvim / packer: inside the nvim-treesitter config
require('nvim-treesitter.parsers').teyru = {
  install_info = {
    url = 'https://github.com/teyru-lang/Teyru',
    location = 'editors/tree-sitter-teyru', -- the grammar is in a subdirectory
    files = { 'src/parser.c' },
  },
}

vim.filetype.add({ extension = { teyru = 'teyru' } })
```

Without nvim-treesitter, build the parser by hand and drop the result where
Neovim looks for parsers:

```sh
cd editors/tree-sitter-teyru
tree-sitter generate
cc -shared -fPIC -I src src/parser.c -o ~/.local/share/nvim/site/parser/teyru.so
```

The queries are picked up from a `queries/teyru/` directory on the runtime
path; copy `queries/*.scm` into `~/.config/nvim/queries/teyru/`.

### Helix

Add to `~/.config/helix/languages.toml`:

```toml
[[language]]
name = "teyru"
scope = "source.teyru"
file-types = ["teyru"]
comment-token = "//"
indent = { tab-width = 2, unit = " " }

[[grammar]]
name = "teyru"
source = { path = "/path/to/Teyru/editors/tree-sitter-teyru" }
```

then run `hx --grammar build`, and copy the queries to
`~/.config/helix/runtime/queries/teyru/`.  Helix reads `@local.scope`,
`@local.definition` and `@local.reference` from `locals.scm`, and the indents
captures from `indents.scm`.

### npm

The package is **not published** and, as it stands, it is not usable as a Node
module: it ships the grammar, the generated parser and the queries, and
nothing else.  `tree-sitter generate` inside a checkout is all that is needed
to build with the `tree-sitter` CLI:

```sh
cd editors/tree-sitter-teyru
npx tree-sitter-cli generate   # writes src/
npx tree-sitter-cli test       # runs test/corpus
npx tree-sitter-cli parse file.teyru
```

There is no `bindings/` directory and no `main` in `package.json`: the Node
binding is generated by `tree-sitter init`, which is interactive, so it was
left out rather than hand-written and untested.  Adding it later means running
`tree-sitter init` here (or copying the node binding from another grammar) and
restoring `main`, `types` and the `bindings/` entry in `files`.

## What is covered

Everything `tests/programs/*.teyru` and `lib/*.teyru` contain, which is the
whole Java-25 surface the compiler implements:

- classes, interfaces, `@interface`s, enums with bodies, records (including
  compact constructors), sealed/non-sealed types, `permits`
- properties: a field followed by `{ get ... set ... }`, with `field` and
  `value` inside the accessors, and `set(name)` for a named setter parameter
- annotations, annotation element values (literals, `{...}` arrays, nested
  annotations, `Name.class`, dotted names) and `default` in an `@interface`
- generics, wildcards, type parameters and bounds, varargs, arrays
- lambdas, method references, local and anonymous classes, initializer blocks
- switch expressions and statements, arrow and colon forms, `yield`, `when`
  guards, `case null`, type patterns, record patterns (including `case Dot()`)
- text blocks, all the literal forms the lexer has, unnamed variables `_`
- try-with-resources (whose resources end at a line break, not at a `;`),
  labels, `assert`, `synchronized`, `throws`
- contextual words: `var`, `val`, `record`, `sealed`, `permits`, `when`,
  `yield`, `field`, `value`, `get`, `set`, `non-sealed`, `module`

## What is not covered

**Line breaks are not tokens.**  Teyru ends a statement at a line break, and
tree-sitter cannot keep a newline as a token while also skipping whitespace
(`extras`), so the grammar guesses where a statement ends and uses precedence
to prefer the reading the compiler's own `parseStatement` prefers.  The guess
is right for the corpus (every file in `tests/programs/` and `lib/` parsed
with no `ERROR` and no `MISSING` node — 86 files when that was checked), but
it is a guess, and three shapes show it:

```teyru
x
-y            // read as one expression statement: `x - y`

a
b             // read as a declaration: type `a`, name `b`

Outer.this.x  // read as `(Outer.this).x` with `this` a field name;
              // `Outer.this` on its own is read correctly
```

The parser never reports an error for these; the tree is simply not the one
the compiler would build.  A grammar that used a `line_break` token could
resolve them, at the cost of having to mention the token everywhere.

The corpus has grown since — 185 files at the last count, the standard library
included — and it has not been re-checked against the parser, so read that 86
as a snapshot rather than a claim about the current tree.

Other deliberate looseness:

- `modifiers` accepts the reserved words in any order and any number, so
  `static public` parses even though the compiler rejects it.
- Error recovery is not tuned; the corpus tests use sources that parse.
- No injections (no grammar for the contents of a text block or a comment).

## Tests

```sh
tree-sitter test          # 15 files, 60 tests, all passing
tree-sitter parse FILE    # print the tree for a file
```

The corpus tests record the trees the parser actually produces, feature by
feature: `basics`, `statements`, `expressions`, `switch`, `patterns`,
`records`, `sealed`, `generics`, `interfaces`, `enums`, `properties`,
`classes`, `literals`, `lambdas`, `annotations`.
